# Постановка — шаблон

**Назначение.** Главный артефакт процесса: по нему пишут код, по нему пишут тесты, по нему ревьюер
проверяет, сделано ли обещанное. **Постановка без сценариев приёмки — не постановка, а тема для
обсуждения.**

**Автор:** аналитик. **Принимает:** разработчик, тестировщик и дизайнер — **три роли, а не одна**
(точка `КТ2`). Разработчик подтверждает выполнимость, тестировщик — проверяемость, дизайнер — наличие
пакета. Одна роль пропускает непроверяемый сценарий, и он обнаруживается на `КТ6`, где переписывать
дорого.

## Требования к содержанию

- **Сценарий приёмки = входные данные + действие + ожидаемый результат.** «Работает корректно» — не
  сценарий; «при двух введённых волнах отчёт показывает их сумму» — сценарий.
- **Отказы и границы данных — отдельными сценариями:** пусто, слишком много, нет прав, внешняя система
  недоступна, предельно длинное значение. Это половина реальных дефектов и та половина, которую
  забывают.
- **У каждого сценария назван способ проверки** — чем он будет закрыт: тест, страж, команда с
  ожидаемым выводом, сверка. Сценарий, который нельзя закрыть ни одним, сформулирован плохо и
  переписывается.
- **Границы — обязательный раздел.** Что сознательно не делаем и почему. Пустой раздел означает, что
  границы не думали, а не что их нет.
- **Открытые вопросы: у каждого назван вариант по умолчанию.** Развилка без умолчания останавливает
  работу на ожидании — самая дорогая форма простоя, потому что незаметная.
- **Зависимости названы адресами:** контракт, миграция, дизайн-пакет, чужая задача.
- Ссылка на требование, из которого выросла. Постановка без требования — работа без заказчика.

## Шаблон

```markdown
# <Имя задачи>

> **Статус:** 🔴 черновик / 🟡 готова к работе / ✅ закрыта <дата>
> **Требование:** <ссылка> | **Заказчик результата:** <имя>
> **Вратарь готовности:** <вывод прогона, дата>

## Зачем
<Что ломается или чего не хватает сегодня и почему это дорого.>

## Что делаем
<Наблюдаемый результат. Не перечень технических шагов.>

## Сценарии приёмки
| № | Сценарий (данные → действие → результат) | Чем закрывается |
|---|---|---|
| 1 | <...> | тест / страж / команда / сверка |
| 2 | **отказ:** <...> | |
| 3 | **граница:** <...> | |

## Границы
| Не делаем | Почему |
|---|---|

## Зависимости
| Что | Адрес | Состояние |
|---|---|---|
| контракт | <ссылка> | утверждён / черновик / нет |
| дизайн-пакет | <ссылка> | полный / нет состояний отказа / нет |
| миграция | <ссылка> | нужна / не нужна |

## Открытые вопросы
| Вопрос | Кому | Вариант по умолчанию |
|---|---|---|

## Приёмка постановки
| Роль | Кто | Подтвердил | Замечание |
|---|---|---|---|
| разработчик — выполнимость | | | |
| тестировщик — проверяемость | | | |
| дизайнер — пакет | | | |
```

## Критерий передачи (проверяет автор)

- [ ] у каждого сценария есть данные, действие и ожидаемый результат;
- [ ] есть хотя бы один сценарий отказа и один граничный;
- [ ] у каждого сценария назван способ проверки;
- [ ] раздел «Границы» не пуст;
- [ ] у каждого открытого вопроса назван вариант по умолчанию;
- [ ] вратарь готовности зелёный, его вывод приложен.

## Критерий приёмки (проверяют три роли, `КТ2`)

- [ ] **разработчик:** я могу это сделать, не расспрашивая автора; зависимости названы и достижимы;
- [ ] **тестировщик:** каждый сценарий я могу проверить и знаю, на каком уровне;
- [ ] **дизайнер:** пакет есть и покрывает все состояния, включая отказы;
- [ ] ни одна роль не подтверждает за другую — три отметки, три имени.
