# Методология работы над ИТ-проектом в AI-first разработке

**Что здесь.** Сами нормы — «как работаем». Они переживают закрытие любого плана и правятся решением,
а не по ходу разговора. Работа по их введению живёт в [plans/](../plans/), шаблоны артефактов — в
[templates/](../templates/).

**Материал абстрактный:** ни имён проектов, ни путей, ни правил конкретного заказчика. Так и держать —
норма, написанная под один проект, во второй не переносится, а переносится приём.

## Четыре посылки, из которых выведено остальное

1. **Контекст сессии конечен и теряется без предупреждения.** Всё, на что опирается работа, лежит в
   файле, а не в диалоге: знание из переписки исчезает при первой компрессии контекста — молча, без
   признака потери.
2. **Агент исполняет постановку буквально, а недосказанное додумывает правдоподобно** — то есть ошибку
   не видно по форме результата. Неизвестное фиксируется вопросом, а не догадкой.
3. **Правило, которое проверяет человек, нарушается молча.** Дисциплина держится до первой спешки;
   машинная проверка нарушается громко и в момент нарушения.
4. **Передача работы между ролями честна ровно настолько, насколько проверяем артефакт передачи.**
   «Договорились на созвоне» — не артефакт; постановка со сценариями приёмки, контракт, матрица
   проверок, релизный чеклист — артефакты.

## Два правила о самих нормах

**Норма без наблюдённого случая нарушения не вводится.** Такие нормы не соблюдают, и они обесценивают
соседние: читатель, однажды увидев неработающее правило, перестаёт верить и работающим.

**Правило, нарушенное дважды, переписывается или механизируется** — не повторяется третий раз. Это и
есть повод к правке этого каталога; журнал правок ведётся здесь же, строкой в файле, который правится.
