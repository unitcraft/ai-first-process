# Релизные заметки и план откатов — шаблон

**Назначение.** Один документ на выпуск: что выходит, в каком порядке применяется, при каком условии
откатывается. Обслуживает и ворота `G6` (готовность кандидата), и `G7` (сам выпуск).

**Автор:** релиз-менеджер. **Принимает:** владелец продукта (что выходит) и DevOps (как выходит).

## Требования

- **Критерий отката назван числом ДО выпуска.** «Если что-то пойдёт не так» — не критерий: в момент
  инцидента решение принимается на панике и с задержкой. Нужны пороги: доля отказов, время отклика,
  число сообщений в очереди.
- **Откат отрепетирован прогоном на `stage`.** План отката, не проверенный прогоном, — это текст. Если
  репетиции не было, это пишется в документ и видно тому, кто разрешает выпуск.
- **Порядок применения жёсткий и записан:** миграции → приложение → переключение флагов. Порядок,
  который «понятен всем», в шесть утра понятен не всем.
- **Миграции перечислены с классом** (см. [migration.md](migration.md)) и с указанием, какие
  необратимы. Необратимая миграция означает, что откат кода **не восстанавливает** прежнее состояние —
  это надо знать до, а не после.
- **Приёмка заказчиком на `stage`** зафиксирована именем и датой. «Согласовано устно» на выпуске не
  считается.
- **Наблюдение после выпуска:** что смотреть, сколько времени, кто дежурит. Выпуск без назначенного
  наблюдателя обнаруживает проблему по обращению пользователя.
- **Changelog собирается из сообщений MR**, а не пишется заново: переписанный вручную расходится с тем,
  что реально влито.

## Шаблон

```markdown
# Релиз <версия>

> **Статус:** кандидат / выпущен <дата, время> / откачен <дата, причина>
> **Релиз-менеджер:** <имя> | **Дежурный после выпуска:** <имя>

## Состав
| Задача | Что стало возможно | MR |
|---|---|---|

## Миграции
| Миграция | Класс | Обратима | Время на копии прод-структуры |
|---|---|---|---|

## Порядок применения
1. <миграции: команда>
2. <приложение: команда>
3. <флаги: что включается и на какую долю>

## Критерий отката — пороги
| Величина | Порог | Где смотреть |
|---|---|---|
| доля отказов | > <N> % за <T> минут | |
| время отклика | > <N> мс, 95-й процентиль | |
| <своя величина> | | |

## Откат
| Шаг | Команда | Отрепетирован на `stage` |
|---|---|---|
| | | да <дата> / **нет** |

**Необратимое в этом релизе:** <перечень или «нет». Если есть — откат кода не восстановит состояние.>

## Репетиция на `stage`
| Что проверено | Результат | Дата |
|---|---|---|
| миграции на копии структуры | | |
| релизный набор тестов | | |
| нагрузка | | |
| приёмка заказчиком | <имя> | |

## Наблюдение после выпуска
<Что смотреть, сколько времени, при каком значении звать дежурного.>
```

## Критерий передачи (проверяет релиз-менеджер, `G6`)

- [ ] критерий отката выражен порогами с числами, а не словами;
- [ ] откат отрепетирован на `stage` — либо явно записано «не отрепетирован»;
- [ ] необратимые миграции перечислены или указано «нет»;
- [ ] приёмка заказчиком зафиксирована именем и датой;
- [ ] changelog собран из сообщений MR;
- [ ] назначен дежурный и срок наблюдения.

## Критерий приёмки

- [ ] **владелец продукта:** я вижу, что выходит, и подтверждаю, что это то, что принимал;
- [ ] **владелец продукта:** необратимые изменения я вижу и принимаю осознанно;
- [ ] **DevOps:** я могу выполнить порядок применения по написанному;
- [ ] **DevOps:** я могу откатить по написанному, и это проверено прогоном.
